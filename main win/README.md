# ProcureFlow Windows 1.0

Самостоятельное локальное приложение для Windows по кейсу HACKALEM AI / Электрокомплект. Этот репозиторий предназначен только для Electron-приложения и сборки EXE. Рекомендуемое имя на GitHub: **procureflow-windows**.

Веб-версия находится в отдельном репозитории **procureflow-web**. Между папками нет символьных ссылок или зависимостей: каждую можно копировать, клонировать и изменять отдельно. Общий расчётный код включён в обе версии; последующие изменения алгоритма нужно переносить в обе версии и проверять тестами.

## Запуск из исходников

Нужны Windows x64 и Node.js 22.12 или новее (для воспроизведения сборки рекомендуется Node.js 24). npm устанавливается вместе с Node.js.

Откройте терминал в этой папке, рядом с package.json:

~~~powershell
npm ci
npm start
~~~

Первое скачивание зависимостей требует интернета. После установки приложение работает локально. При запуске из среды, где задана переменная ELECTRON_RUN_AS_NODE, сначала удалите её только из текущего процесса:

~~~powershell
Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
npm start
~~~

Можно дважды щёлкнуть **START-WINDOWS.cmd**: он проверит Node.js, при необходимости установит зависимости и откроет приложение. Повторный запуск не переустанавливает зависимости. После обновления package-lock.json выполните npm ci вручную.

## Сборка приложения

~~~powershell
npm ci
npm test
npm run check:offline
npm run dist:win
~~~

Либо запустите **BUILD-WINDOWS.cmd**. Сборка создаёт:

- dist/ProcureFlow-Portable-1.0.0-x64.exe — запуск без установки;
- dist/ProcureFlow-Setup-1.0.0-x64.exe — установщик для текущего пользователя.

Node.js нужен для запуска исходников и сборки. Для готового EXE он не требуется. Исходный репозиторий не содержит EXE; получите их локальной сборкой или через GitHub Actions.

## Сборка на GitHub без локальных инструментов

Workflow находится только в **.github/workflows/build-windows.yml**. Он запускается при push в main/master, при pull request и вручную. Проверяет расчёты, локальные ресурсы и зависимости, собирает EXE и запускает проверку упакованного приложения.

1. Откройте вкладку **Actions → Build Windows EXE**.
2. Дождитесь успешного запуска либо нажмите **Run workflow**.
3. Откройте завершённый запуск и раздел **Artifacts**.
4. Скачайте **ProcureFlow-Windows-x64**, распакуйте архив и запустите Portable либо Setup.

Для скачивания артефактов обычно нужен вход в GitHub. Артефакт хранится 14 дней; при необходимости повторите workflow. Workflow не публикует сайт, релиз и не отправляет заказы. В этом репозитории не нужно включать GitHub Pages.

## Первый расчёт
1. На странице «Загрузка данных» выберите IEK.zip и Systeme electric.zip. Распаковка выполняется локально. Можно загрузить отдельные XLSX/CSV.
2. Проверьте журнал источников и дату среза. Все 12 таблиц предоставленных архивов поддерживаются.
3. В параметрах укажите сроки поставщиков, цикл заказа, страховой запас, плановый рост и при необходимости правила категорий.
4. По умолчанию рассчитывается общий запас. Для отдельного склада выберите его в параметрах. Если его остаток не передан, приложение не распределяет общий запас произвольно.
5. Откройте артикул: видны формула, сезонность, тренд, исключённые продажи и компенсация stockout. Неизвестный остаток можно уточнить в разделе «Данные товара».
6. При необходимости измените количество с соблюдением MOQ и кратности.
7. На странице «Поставщики» проверьте позиции, укажите ответственного и подтвердите проверку. Приложение создаст файл, но ничего не отправит поставщику.
8. Сохраните проект, чтобы продолжить позже. После открытия нужно повторно утвердить заказ.

## Обмен с 1С
Кнопка «Экспорт для 1С» на странице поставщиков создаёт XLSX/CSV только с утверждёнными положительными количествами.
Укажите организацию и склад; названия колонок настраиваются под обработку загрузки вашей 1С.
Поля: код 1С, артикул, наименование, поставщик, склад, единица, количество, дата, организация, ответственный, обоснование.
CSV — UTF-8 с BOM, разделитель «;». XLSX сохраняет коды как текст, количества как числа. Формулы из текстовых значений не выполняются.
Это универсальный табличный обмен. Загрузка в конкретную базу 1С требует сопоставления колонок и проверки в тестовой базе.

## Универсальный шаблон
В интерфейсе доступен XLSX-шаблон с синтетическими примерами.
- Catalog: sku, code, name, supplier, category, cost, stock, multiple, moq, lead_days, growth_pct, warehouse, unit.
- Sales: date, sku, qty, client_id, order_id, warehouse, supplier, price.
- Stockouts: sku, start_date, end_date, warehouse, supplier.
- Transit: sku, qty, eta, order_id, warehouse, supplier.
- Seasonality: month, factor (12 положительных коэффициентов).
Даты — YYYY-MM-DD. Коды и артикулы храните текстом. Пустой остаток означает «неизвестен», ноль — подтверждённое отсутствие.
Цена продажи не используется как замена количеству спроса. Денежная оценка закупки использует себестоимость.
Противоречивые остатки блокируют рекомендацию до уточнения. Поставки одного документа не должны повторяться в разных источниках.
Каталоги разделяются по поставщикам; дополнительные источники связываются по однозначным кодам/артикулам.

## Методология
### История и выбросы
Подробные продажи служат резервной историей при отсутствии месячных итогов и источником выявления аномалий. Дважды они не суммируются.
Положительные строки группируются по SKU, дате и обезличенному клиенту; без клиента — по номеру документа.
При наличии не менее восьми групп порог равен max(8 × median, median + 8 × MAD, 10).
Группы выше порога исключаются при включённой очистке. При неполном покрытии детализацией дополнительно проверяются месячные пики после снятия сезонности. Наличие нескольких документов не отключает месячную проверку.
Кандидаты остаются видны в карточке. Это объяснимая эвристика, требующая проверки крупных событий менеджером.

### Сезонность, рост, текущий месяц
Для SKU с двумя полными историческими годами строится месячный профиль. Если есть загруженная сезонность, итоговый профиль использует 80% собственного и 20% загруженного.
При короткой истории используются загруженные коэффициенты; без них коэффициент равен 1 с предупреждением.
Основа — дневной очищенный и десезонализированный спрос за последние шесть завершённых месяцев.
Тренд = median(последние 3 месяца) / median(предыдущие 3) − 1, ограниченный ±50%; вперёд переносится половина сдвига.
После семи дней текущий месяц учитывается с весом полноты. Плановый прирост товара и общий прирост складываются. Правила категорий изменяют спрос и запас.
Срок товара приоритетнее срока поставщика, затем категории, затем общего срока.

### Stockout
Интервалы объединяются без задвоения дней.
При положительных продажах спрос пересчитывается на число доступных дней.
При нулевых продажах отсутствующие дни оцениваются по медианной дневной ставке доступной истории с сезонностью.
При отсутствии любой положительной истории спрос не выдумывается. Оценка по двум нулевым месячным остаткам включается отдельно и обозначается как допущение.

### Заказ
Горизонт = срок поставки + цикл пересмотра.
Потребность = max(0, прогноз на горизонт + страховой запас − остаток − своевременные поставки).
Если потребность положительна: ceil(max(потребность, MOQ) / кратность) × кратность.
Нулевая потребность не запускает MOQ. Поставки после горизонта и просроченные поставки не вычитаются. Недатированные — только при явном включении допущения.
Расчёт не выдаёт NaN/Infinity как нулевой заказ: некорректные числа останавливают операцию.

## Приватность и ограничения
- Сетевые запросы интерфейса запрещены; нет облака, аналитики, API-ключей или отправки заказа.
- При импорте client_id и распознанные клиентские колонки заменяются локальными HMAC-SHA256 идентификаторами до расчёта.
- Неизвестные произвольные поля могут содержать чувствительный текст. Используйте согласованную обезличенную выгрузку; исходные листы не сохраняются в проект.
- Проект содержит коммерческие показатели и локальный журнал в открытом JSON. Храните его в защищённом месте; учитывайте синхронизацию папки OneDrive.
- Журнал — локальная история, не электронная подпись и не система разграничения полномочий.
- Тестовые архивы не содержат точных stockout, обезличенных клиентов и полного справочника сроков. Эти функции испытаны на синтетических сценариях и доступны через шаблон.
- Остатки в данных частично отсутствуют. Не включайте «пустые остатки = 0» без проверки.
- Лимит файла/ZIP — 25 МБ, распаковки контейнера — 120 МБ, проекта — 80 МБ. XLS, XLSB и зашифрованный Excel не поддерживаются.
- Полная история прогноза и экономический эффект требуют ретроспективной проверки на данных компании. Установка в рабочую базу 1С не тестировалась.

## Проверки

~~~powershell
npm test
npm run check:offline
npm run test:desktop
~~~

npm test запускает 60 проверок: расчёты, формат проектов, статическую защиту Electron и сценарии ТЗ. test:desktop дополнительно запускает приложение и проверяет интерфейс, утверждение заказа, экспорт и повторное чтение XLSX, обмен для 1С, обезличивание и восстановление проекта.

После сборки можно проверить именно упакованное приложение:

~~~powershell
Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
$env:PF_SMOKE_OUTPUT = Join-Path $PWD 'dist/desktop-smoke.json'
$app = Join-Path $PWD 'dist/win-unpacked/ProcureFlow.exe'
$process = Start-Process -FilePath $app -ArgumentList '--smoke-test' -WindowStyle Hidden -PassThru -Wait
if ($process.ExitCode -ne 0) { throw 'Desktop smoke test failed' }
Get-Content $env:PF_SMOKE_OUTPUT
~~~

Для проверки собственных архивов задайте PF_REAL_ARCHIVES как JSON-массив абсолютных путей перед запуском smoke-теста. В отчёт выводятся агрегаты, без исходных строк. Приватные архивы в репозиторий не входят.

Поведение расчётного ядра сохранено при отделении Windows-версии. Проверки не заменяют приёмку формата обмена в тестовой базе 1С, ретроспективную проверку прогноза и испытание установки в вашей организации.

## Структура

- assets/engine.js — распознавание исходных форматов.
- assets/planner.js — проверка и объединение данных, расчёт.
- assets/privacy.js и assets/engine-worker.js — обезличивание и фоновый импорт.
- assets/xlsx.js — локальное чтение ZIP/XLSX/CSV и экспорт XLSX.
- assets/app.js — сценарий закупщика и обмен с 1С.
- assets/project.js — формат проекта и проверка данных.
- desktop/ — защищённая Electron-оболочка и проверка интерфейса.
- tests/ — воспроизводимые проверки.
- build/ — иконки приложения.
- docs/DESKTOP.md — подробная инструкция Windows.
- .github/workflows/build-windows.yml — единственный workflow этого репозитория.
