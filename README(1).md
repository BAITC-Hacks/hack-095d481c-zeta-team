# ProcureFlow

### Универсальное рабочее место закупщика — Web + Windows Offline

**От Excel к обоснованному заказу поставщику. Данные обрабатываются локально, решение остаётся за менеджером.**

ProcureFlow объединяет отчёты о продажах, остатках и поставках, рассчитывает потребность в пополнении и объясняет рекомендуемое количество по каждому товару. Вместо ручного сведения нескольких Excel менеджер получает единый список закупки, видит риск дефицита, проверяет допущения и экспортирует результат.

Один продукт работает в двух форматах: **в браузере — без отдельного backend и API-ключей; на Windows — как автономное приложение со встроенным интерфейсом и расчётным ядром**. Windows-версия не открывает опубликованный сайт внутри оболочки: она использует локальные файлы приложения.

> **Наше предложение:** объяснимая закупка без обязательной передачи коммерческих данных облачному сервису, с возможностью продолжить работу в автономном Windows-приложении.

**Статус:** MVP v0.2.0. В репозитории находятся исходники веб-версии и Windows-приложения, а не готовые EXE. Инструкции сборки приведены ниже; фактический статус проверок — в [отчёте](docs/VERIFICATION.md).

## Какую конкретно проблему из ТЗ мы решаем

Кейс: **«Автоматический расчёт заказов поставщикам для пополнения склада»**. Основной пользователь — менеджер отдела закупа.

По условиям кейса менеджер вручную консолидирует данные в Excel. Детальный расчёт занимает много усилий, поэтому выполняется нечасто. В результате по одним товарам появляются избыточные запасы, по другим — дефицит. При этом разовый крупный заказ, в том числе продажа одному клиенту, может ошибочно выглядеть как устойчивый спрос и завысить следующую закупку.

**Задача ProcureFlow — превратить разрозненные выгрузки в проверяемое решение: что заказать, у какого поставщика, в каком количестве, насколько срочно и почему.** Для этого недостаточно среднего объёма продаж: нужно учесть сезонность, рост, периоды отсутствия товара, текущий остаток и уже ожидаемые поставки.

Ожидаемая ценность соответствует ТЗ: снижение избыточного хранения, сокращение дефицита и упущенных продаж, повышение обоснованности регулярных закупок. Это **цели внедрения**, а не уже доказанная экономия: её размер и точность прогноза необходимо измерить на данных компании.

## Как работает решение

```text
Excel / CSV
    ↓
Распознавание источников и объединение товаров
    ↓
Проверка данных и явное отображение допущений
    ↓
Выявление разовых пиков → восстановление спроса при отсутствии товара
    ↓
Базовый спрос + сезонность + тренд + плановый прирост + правила категорий
    ↓
Остаток + ожидаемые поставки + сроки + минимальная партия + кратность
    ↓
Рекомендации, срочность и объяснение по каждой позиции
    ↓
Проверка и корректировка менеджером → подтверждение → экспорт
```

Пользователь загружает файлы, проверяет дату среза и параметры, затем получает дашборд и таблицу рекомендаций. В карточке **«Почему?»** доступны исходные компоненты расчёта, история спроса, найденные аномалии и сценарий изменения параметров. Заказы группируются по поставщикам.

Количество рассчитывает **детерминированное математическое ядро**, а не генеративная модель. Одинаковые данные, настройки и версия ядра дают одинаковый результат. Объяснения формируются из рассчитанных значений; для работы не нужен внешний AI API.

## Чем ProcureFlow выделяется

### 1. Не только сайт, а автономное рабочее место

Веб-версия удобна для первого знакомства и запуска по ссылке. Windows-версия предназначена для работы без подключения к сервису: расчёт, разбор Excel, интерфейс и экспорт включены в приложение. Предусмотрены Portable EXE и установщик.

**Ценность:** менеджеру не нужно передавать исходные выгрузки удалённому вычислительному сервису или держать сайт открытым для работы в Desktop.

### 2. Единый проект между Web и Desktop

Файл `.pfproject` сохраняет загруженные таблицы, параметры, ручные количества и статусы подтверждения. Его можно открыть в другой версии приложения с совместимым форматом. При открытии рекомендации пересчитываются общим ядром.

**Ценность:** можно начать разбор в браузере, сохранить проект и продолжить на Windows. Перенос выполняется вручную; автоматической облачной синхронизации нет.

### 3. Проверяемое решение вместо необъяснимой цифры

Менеджер видит не только «заказать 120», но и спрос на горизонт, страховой запас, вычтенный остаток, учтённые поступления и округление. Сценарный расчёт позволяет изменить остаток, срок или количество в пути и увидеть изменение рекомендации.

**Ценность:** результат можно проверить, обсудить и скорректировать до формирования заказа. Ручная корректировка не скрывает исходную рекомендацию.

### 4. Неопределённость не маскируется под факт

Неизвестный остаток не превращается автоматически в ноль. Поставки без даты, просроченные поступления и недостающие сведения помечаются отдельно. Поставщик и срок из настроек обозначаются как допущения, когда их нет в справочнике.

**Ценность:** менеджер понимает, какие рекомендации готовы к проверке, а где сначала нужно уточнить данные.

### 5. Универсальность через единую модель данных

Расчёт опирается на товары, продажи, поставщиков, остатки и поставки, а не на конкретный бренд. Для исходных отчётов SystemElectric предусмотрено распознавание форматов; для других источников — единый шаблон Excel.

**Ценность:** другой компании не нужно повторять структуру исходных отчётов кейса — достаточно подготовить данные по шаблону. При этом MVP **не обещает автоматически понимать произвольный Excel**: неизвестный формат необходимо привести к шаблону или добавить для него адаптер.

**Наша отличительная комбинация — автономность, локальная обработка, объяснимость и управляемое решение в одном рабочем процессе.** Наличие EXE само по себе не делает прогноз точнее; преимущество — в способе использования и контроле данных.

## Безопасность: какие меры заложены в приложение

Базовый принцип — **не передавать исходные коммерческие данные туда, где они не нужны для расчёта**. Обработка выполняется на устройстве пользователя. Ниже перечислены конкретные ограничения в коде, а не обещание абсолютной защищённости.

| Мера | Как реализовано |
|---|---|
| Локальная обработка | Парсер Excel, расчёт и экспорт работают внутри браузера или Windows-приложения. Отправка загруженных таблиц на backend не предусмотрена. |
| Локальные зависимости интерфейса | В комплекте находятся скрипты, стили, графики и XLSX-парсер. Внешние CDN, аналитические трекеры и AI API не подключены. |
| Ограничение сетевых соединений | В [странице](index.html) задана CSP `connect-src 'none'`. В [Windows-оболочке](desktop/main.cjs) дополнительно блокируются HTTP(S), WebSocket, FTP, произвольные `file://` запросы, внешняя навигация и новые окна. |
| Изоляция интерфейса Windows | В Electron включены `contextIsolation` и `sandbox`, отключён `nodeIntegration`. Доступ к системным операциям идёт через ограниченные IPC-команды с проверкой отправителя. |
| Контролируемая обработка файлов | Формулы Excel не выполняются: читаются их сохранённые результаты. Применяются лимиты размера, проверки структуры XLSX и формата проекта. |
| Контроль действий менеджером | Нет автоматической отправки заказа поставщику. Сохранение проекта выполняется по действию пользователя; автоматической загрузки проекта в облако нет. |

**Границы защиты.** `.pfproject` содержит коммерческие данные и исходные листы в незашифрованном виде. Сами экспортированные XLSX также не шифруются приложением. Пользователь с доступом к файлам может их прочитать; статус подтверждения не является электронной подписью или защищённым журналом аудита. Клиентские сведения нужно обезличить **до загрузки** — автоматической анонимизации нет.

При открытии веб-версии браузер обращается к хостингу за файлами сайта; это не означает отправку выбранных Excel. Сетевые ограничения приложения не управляют сетью ОС, расширений браузера и защитного ПО. Electron создаёт стандартный локальный профиль, но автоматическое сохранение Excel в него не предусмотрено.

MVP не проходил независимый аудит безопасности и не заявляет сертифицированную защиту. Windows-сборка пока не подписана сертификатом издателя. Для корпоративного внедрения необходимы проверка IT-службой, подпись релиза и правила хранения рабочих файлов. **Не публикуйте коммерческие Excel и `.pfproject` в репозитории.** Подробнее: [Desktop и приватность](docs/DESKTOP.md).

## Входные данные и универсальный шаблон

Для кейса поддерживаются шесть типов исходных выгрузок: динамика продаж, ежемесячные продажи, ежемесячные остатки, сводная ведомость с товаром в пути, сезонность и MOQ/кратность. Данные объединяются по коду 1С и артикулу; код и артикул рекомендуется хранить как текст, чтобы сохранить ведущие нули.

Для других источников нажмите **«Скачать шаблон»** и замените вымышленные примеры своими данными:

| Лист | Основные поля |
|---|---|
| `Catalog` | `sku`, `code`, `name`, `supplier`, `category`, `cost`, `stock`, `multiple`, `moq`, `lead_days`, `growth_pct` |
| `Sales` | `date`, `sku`, `qty`, `client_id` — только обезличенный, `order_id` |
| `Stockouts` | `sku`, `start_date`, `end_date` — обе границы включительно |
| `Transit` | `sku`, `quantity`, `eta` |
| `Seasonality` | `month` — от 1 до 12, `factor` |

Даты рекомендуется передавать в формате `YYYY-MM-DD`. XLSX должен содержать сохранённые результаты формул: приложение не пересчитывает саму книгу. CSV поддерживается в UTF-8; XLS, XLSB и книги с паролем не поддерживаются. Для импорта XLSX в браузере требуется `DecompressionStream('deflate-raw')`.

**Порядок сведения данных:** отдельные месячные продажи приоритетнее месячных колонок сводной ведомости; детализация используется как источник месячной суммы только там, где агрегата нет. Свободный остаток сводной ведомости приоритетнее месячного среза. Это предотвращает повторное прибавление одной и той же продажи из разных типов отчётов.

Файл с тем же именем заменяет предыдущую загруженную версию. Универсального разрешения конфликтов между перекрывающимися выгрузками под разными именами нет. Не загружайте несколько копий одной детализации. Неизвестные листы показываются в журнале и не участвуют в расчёте.

Перед расчётом согласуйте организацию, склад, период, единицы измерения и дату среза во всех источниках. Изменение даты в настройках не восстанавливает исторический остаток. Короткие даты поставок без года нужно проверить; текущий адаптер сводной ведомости берёт год из даты имени файла, а при её отсутствии использует 2026.

## Методология расчёта

Реализация: [assets/engine.js](assets/engine.js). Это прозрачная эвристическая модель для MVP, а не обученная ML-модель или оптимизатор бюджета.

### Базовый спрос, сезонность и рост

Используется история до 12 завершённых месяцев перед датой среза. Текущий неполный месяц не включается в среднее; отрицательная месячная нетто-продажа после возвратов ограничивается нулём для прогнозирования. В детализации отрицательные количества учитываются как возвраты, а строки документа «Заказ» исключаются.

После обработки аномалий и stockout месячный спрос переводится в дневной и очищается от сезонного коэффициента. База — средняя дневная ставка последних доступных шести месяцев. Сезонный профиль нормируется к среднему 1 и применяется к будущим календарным дням.

Устойчивый сдвиг оценивается отношением медиан последних трёх и предыдущих трёх дневных ставок, с ограничением от −50% до +50%. При недостатке истории тренд равен нулю. Поскольку свежий спрос уже участвует в базе, переносится половина сдвига: множитель `1 + trend / 2`.

Дополнительно применяются общий плановый прирост, `growth_pct` товара и множитель категории. Категория может задавать страховой запас и срок поставки по умолчанию; явный срок товара приоритетнее. Отдельная настройка позволяет использовать «Кэф. Роста» из ведомости вместо рассчитанного тренда — трактовку этого поля необходимо согласовать с владельцем данных.

### Исключение разовых крупных заказов

Положительные продажи объединяются внутри артикула по дате и документу. При наличии обезличенного клиента используется его дневной объём по этому товару. Для не менее восьми групп порог определяется так:

```text
Порог = max(8 × median, median + 8 × MAD, Q3 + 6 × IQR, 10)
```

`median` — медиана объёмов; `MAD` — медиана абсолютных отклонений от медианы; `IQR` — разность третьего и первого квартилей.

Группа выше порога помечается как кандидат на разовый заказ. При включённой очистке её объём исключается из соответствующего месяца, не опуская месячную продажу ниже нуля. При недостаточной детализации и наличии минимум шести ненулевых месяцев используется резервная проверка месячных пиков после снятия сезонности. Она **не заменяет** анализ конкретного клиента.

Крупная продажа может быть реальным изменением спроса: обнаружение не доказывает её разовый характер. Менеджер должен проверить такие события. Клиентские ID и номера документов не включаются в итоговый экспорт рекомендаций, но исходные листы остаются в сохранённом `.pfproject`.

### Упущенный спрос при отсутствии товара

Интервалы `Stockouts` объединяются без повторного учёта совпадающих дней. Для частично доступного месяца:

```text
Восстановленный спрос = очищенные продажи × дни месяца / доступные дни
```

Полностью недоступный месяц оценивается по медианной дневной ставке доступных месяцев с учётом сезонности. **Коррекция вносится один раз в историю**, а не добавляется повторно к итоговому заказу.

Два нулевых месячных остатка не доказывают отсутствие товара весь месяц. Поэтому приблизительная компенсация по остаткам отключена по умолчанию. При недостаточной истории надёжно восстановить потерянный спрос невозможно; требуется проверка исходных данных.

### Количество к заказу

```text
Горизонт = срок поставки + цикл пересмотра заказа.
Прогноз = сумма дневного спроса по календарным дням горизонта.
Страховой запас = спрос на дополнительные дни после горизонта.
Потребность = max(0, прогноз + страховой запас − остаток − учтённые поставки).

Если потребность > 0:
    Заказ = ceil(max(потребность, минимальная партия) / кратность) × кратность.
Иначе:
    Заказ = 0.
```

**Минимальная партия и кратность — разные параметры.** В исходном файле MOQ используется фактический столбец «Кратность»; минимальная партия не выдумывается.

В покрытие входят положительные поставки после даты среза и до конца горизонта. Просроченные и более поздние поступления не вычитаются как своевременное покрытие. Поставки без даты исключены по умолчанию; включить их можно только как явное допущение. При неизвестном текущем остатке числовая рекомендация не формируется без уточнения или отдельного допущения пользователя.

Риск дефицита оценивается дневной симуляцией запаса и датированных поступлений до срока новой поставки. Изменение общего количества «в пути» в сценарии влияет на заказ, но не создаёт новый график дат поступлений.

### Что получает менеджер

Рекомендации содержат артикул, поставщика, количество, срочность и обоснование. Экспорт XLSX включает листы **«Заказы»**, **«Параметры и метод»**, **«Источники»**. Выгрузка из списка рекомендаций учитывает активные фильтры.

Денежная сумма — оценка только по товарам с известной положительной себестоимостью. Поле «СС реал» используется как приближение себестоимости, валюта задаётся вручную. Это не подтверждённая закупочная цена и не гарантированный бюджет. При пересчёте параметров ручные количества и подтверждения сбрасываются, чтобы менеджер повторно проверил изменившееся решение.

## Запуск

### Веб-версия

Для локального старта распакуйте репозиторий и откройте `index.html` в совместимом браузере. Установка npm-зависимостей и сборка веб-интерфейса не нужны. Альтернативный запуск из папки проекта:

```bash
python3 -m http.server 8000
```

Адрес: `http://localhost:8000`.

Для GitHub Pages загрузите содержимое репозитория так, чтобы `index.html` находился в корне рядом с `assets`. В настройках Pages выберите публикацию из ветки `main`, папка `/(root)`. В репозитории публикуется **код**, а не коммерческие Excel. Доступность публикации зависит от настроек вашего аккаунта и организации.

При первом открытии показаны явно обозначенные синтетические демоданные. Для расчёта компании загрузите свои файлы и проверьте параметры. Перед закрытием сохраните `.pfproject`: автоматического восстановления несохранённой работы нет.

### Сборка EXE непосредственно на Windows

Для разработчика: Windows x64, Node.js 22 и интернет на время установки инструментов. Распакуйте весь репозиторий и запустите **`BUILD-WINDOWS.cmd`** рядом с `package.json`.

Альтернативно откройте **cmd** в папке проекта:

```bat
set "CSC_IDENTITY_AUTO_DISCOVERY=false"
npm install --no-audit --no-fund && npm test && npm run check:offline && npm run dist:win
```

После успешной сборки в `dist` ожидаются:

```text
ProcureFlow-Portable-0.2.0-x64.exe    — запуск без установки
ProcureFlow-Setup-0.2.0-x64.exe       — установщик
```

Менеджеру передаётся Portable или установщик; Node.js и исходники для работы готового приложения не нужны. Не передавайте отдельно `ProcureFlow.exe` из `win-unpacked` без соседних файлов. Перед демонстрацией необходимо проверить собранную программу на целевом Windows-компьютере.

Сборка через GitHub Actions остаётся альтернативой: [docs/DESKTOP.md](docs/DESKTOP.md). Блокировка Actions не препятствует локальной сборке при наличии необходимых инструментов.

## Проверки и готовность

```bash
npm test
npm run check:offline
```

В комплекте 36 тестов: 14 расчётных, 11 проверок файлов проектов и 11 проверок ограничений маршрутизации и статической конфигурации Desktop. Они проверяют, в частности, влияние источников на расчёт, MOQ/кратность, stockout, подавление месячного пика, восстановление проекта и ограничения доступа к ресурсам.

В отчёте подготовки v0.2 зафиксированы успешные модульные проверки и сценарии интерфейса в Chromium/Linux, включая импорт шести исходных XLSX, сохранение/восстановление проекта и повторное открытие экспортированного XLSX. **Это не подтверждение запуска Windows EXE, аудита безопасности или точности закупок на реальных будущих продажах.** Подробности среды и границы проверок: [docs/VERIFICATION.md](docs/VERIFICATION.md).

### Демонстрация перед жюри

На проверенном Windows-ПК отключите интернет, запустите EXE и загрузите обезличенные тестовые Excel. Покажите рекомендацию и «Почему?», измените срок или объём в пути, затем экспортируйте результат. Сохраните `.pfproject`, закройте приложение и откройте проект снова. Такой сценарий показывает **автономность, объяснимость и сохранение рабочего контекста**, а не только внешний вид интерфейса.

## Границы MVP и дальнейшее развитие

Сейчас приложение использует агрегированный остаток: отдельное планирование и распределение по складам не реализованы. Нет учётных записей, общей БД, совместного редактирования, прямого обмена с 1С и API поставщиков. XLSX-экспорт требует проверки совместимости с конкретной конфигурацией учётной системы; это не готовый коннектор.

Лимиты: входной файл — 25 МБ, распакованный XLSX — 120 МБ, файл проекта — 80 МБ. Макросы, внешние ссылки и ZIP64 не поддерживаются. Без точных stockout и обезличенных клиентских ID соответствующие сценарии нельзя достоверно подтвердить на исходном наборе партнёра.

Перед промышленным внедрением необходимы проверка прогноза на отложенных периодах, оценка бизнес-эффекта, аудит безопасности и подпись Windows-релиза. Направления дальнейшей разработки — шифрование проектов, разграничение доступа и защищённая история согласований, многоскладское планирование и адаптеры учётных систем. **Эти возможности не входят в текущую версию.**
