# ProcureFlow — закупки из Excel

Готовый статический MVP для GitHub Pages. Не нужны сервер, база данных, ключи API, npm install или сборка. Интерфейс на русском языке. Все вычисления выполняются в браузере.

## Быстрый запуск на GitHub Pages

1. Распакуйте архив.
2. Создайте GitHub-репозиторий, например `procureflow`. Для самого простого сценария используйте Public, **но не добавляйте туда коммерческие Excel**.
3. Через **Add file → Upload files** загрузите содержимое распакованной папки. `index.html` должен находиться непосредственно в корне репозитория, рядом с папкой `assets`. Загружайте именно файлы и папки, не ZIP.
4. Нажмите **Commit changes**.
5. Откройте **Settings → Pages → Build and deployment**.
6. Выберите **Source: Deploy from a branch**, затем **Branch: main**, папку **/(root)** и нажмите **Save**.
7. После успешной публикации откройте ссылку, которую покажет GitHub Pages.
8. На первом экране работают синтетические демонстрационные данные. Нажмите **Загрузить Excel** и выберите все шесть исходных файлов кейса одновременно.
9. Перейдите в **Параметры расчёта**, проверьте дату среза, срок поставки, цикл пересмотра, страховой запас, валюту и поставщика по умолчанию.

Официальная инструкция GitHub: https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site

Для обновления замените изменённые файлы в репозитории и сделайте Commit. После публикации обновите страницу без кэша. Не создавайте лишнюю вложенную папку с `index.html`: при таком размещении изменится адрес сайта.

## Локальный запуск

Откройте `index.html` в современном браузере. Скрипты обычные, без модулей и fetch, поэтому сервер не обязателен. Альтернативный способ из папки проекта:

```bash
python3 -m http.server 8000
```

Адрес локального сервера: `http://localhost:8000`.

Для XLSX браузер должен поддерживать `DecompressionStream('deflate-raw')`. При отсутствии поддержки приложение покажет понятную ошибку. Используйте браузер с поддержкой API либо CSV UTF-8. Старый формат XLS и зашифрованные книги не поддерживаются.

- Что-если сценарий по артикулу, ручная корректировка количества, группировка по поставщикам, явное подтверждение заказа.
- Экспорт XLSX с листами «Заказы», «Параметры и метод», «Источники». Экспорт из рекомендаций учитывает активные фильтры.
- Шаблон XLSX для других источников: справочник, продажи, stockouts, поставки, сезонность.
- Синтетический демонабор: 42 SKU и 3 поставщика, явно обозначен как демо.
- Адаптивная мобильная версия, без внешних шрифтов, трекеров, CDN и сетевых запросов приложения.

## Как читать исходные файлы

| Источник | Что используется | Приоритет / ограничение |
|---|---|---|
| Ежемесячные продажи | Код, артикул, количество по месяцам, кратность | Основная месячная история; пустые месячные продажи трактуются как 0 |
| Динамика продаж | Дата, код, количество, номер документа | Проверка разовых заказов; не прибавляется повторно к месячным итогам |
| Ежемесячные остатки | Код и остатки по месяцам | Последний столбец как текущий срез, только при отсутствии более приоритетного остатка |
| Товар в пути / сводная ведомость | Свободный остаток, категория, СС реал, поступление 24.09, артикул, код | Свободный остаток имеет приоритет. Суммы по складам повторно не суммируются |
| MOQ | Код ↔ артикул, «Кратность» | Положительное значение задаёт упаковочную кратность |
| Сезонность | Итоговый столбец «СЕЗОННОСТЬ» | Коэффициенты нормируются к среднему 1. Общая сезонность — прокси, не индивидуальная модель каждого SKU |

Отдельные помесячные продажи имеют приоритет над месячными колонками сводной ведомости. Если для конкретного месяца ни одного агрегата нет, используется сумма детализации за этот месяц. Скрытые листы пропускаются, чтобы не импортировать служебные копии. Формулы Excel **не исполняются**: читаются сохранённые результаты формул; для пересчитанных вручную книг сохраните файл в Excel перед загрузкой.

Файл с тем же именем заменяет свою предыдущую версию. Перекрывающиеся выгрузки под разными именами пока не поддерживают универсальное разрешение конфликтов. Не загружайте несколько копий одной детализации под разными именами. Порядок приоритетов форматов сохраняется; внутри одного приоритета последнее прочитанное значение заменяет предыдущее.

## Методология

### 1. Базовый спрос

Для моделирования используется до 12 **завершённых** месяцев перед датой среза. Текущий неполный месяц исключается из среднего. Отрицательная месячная нетто-продажа после возвратов ограничивается нулём для прогнозирования. В детализации положительное количество считается продажей, отрицательное — возвратом/сторно; строки документа «Заказ» исключаются.

После исключения аномалий и компенсации stockout месячный спрос делится на количество дней и сезонный коэффициент. Базовая ставка — среднее полученных дневных ставок последних 6 месяцев. Это прозрачная эвристика, а не обученная ML-модель.

### 2. Аномалии

Положительные строки объединяются по дате и номеру документа; если есть обезличенный клиент — по дате и клиенту внутри артикула. При не менее 8 группах рассчитывается порог:

```text
max(8 × median, median + 8 × MAD, Q3 + 6 × IQR, 10 единиц)
```

Объём группы выше порога считается кандидатом на разовую продажу и при включённой настройке исключается из соответствующего месяца, не более его фактических продаж. Номера документов и клиентские идентификаторы не выводятся в экспорт.

При недостаточной детализации и наличии минимум 6 ненулевых месяцев применяется консервативная проверка месячных пиков после снятия сезонности. Аномальный месяц заменяется медианным нормализованным значением остальных непиковых месяцев. Это не эквивалент обнаружения заказа конкретного клиента.

Нужно сверять, что месячные итоги и детализация охватывают одну организацию/склад/период. Автоматической сверки полноты детализации с месячными итогами в v0.1 нет. Алгоритм может ошибочно убрать реальный рост или не заметить аномалию; крупные события требуют проверки менеджером.

### 3. Stockout

Точные интервалы из листа `Stockouts` объединяются по датам без задвоения. Для неполной доступности спрос = продажи × дни месяца / доступные дни. Полностью отсутствующий месяц оценивается по медианной дневной ставке доступных месяцев с учётом сезонности. Поправка вносится **один раз в историю**, не добавляется вторично к итоговому заказу.

В исходном наборе нет точного журнала отсутствия товара. По двум нулевым месячным срезам нельзя доказать полный месяц отсутствия. Поэтому такая приблизительная компенсация выключена по умолчанию и включается отдельно. Пустые остатки не считаются нулевыми без ещё одного явного допущения.

### 4. Тренд, категории и плановый прирост

Собственный тренд = median(последние 3 дневные ставки) / median(предыдущие 3) − 1, с ограничением ±50%. Если сравнение невозможно, тренд = 0. Поскольку последние месяцы уже включены в базу, применяется множитель `1 + trend / 2`.

По отдельной настройке вместо собственного тренда используется столбец «Кэф. Роста» ведомости как относительный прирост (ограничение от −80% до +100%). Его семантику необходимо подтвердить у партнёра. Применяется тот же принцип переноса половины сдвига.

Далее применяются плановый рост из настроек плюс `growth_pct` товара, и множитель категории. Категория может также задавать срок поставки по умолчанию и страховой запас; явный срок товара приоритетнее. Категории «1», «2» и т.д. не получают вымышленных значений.

### 5. Заказ

```text
Горизонт = срок поставки + цикл пересмотра заказа.
Прогноз = сумма дневного спроса по календарным дням горизонта.
Страховой запас = спрос на дополнительные дни после горизонта.
Потребность = max(0, прогноз + страховой запас − доступный остаток − учтённые поставки).
Если потребность > 0:
  Заказ = ceil(max(потребность, минимальная партия) / кратность) × кратность.
Иначе заказ = 0.
```

При неизвестном текущем остатке рекомендация количества не формируется, пока не введено отдельное допущение о нуле либо ручная корректировка. Неизвестный остаток нельзя молча заменять последним старым ненулевым значением.

В покрытие входят поставки после даты среза и до конца горизонта. Просроченные исключены до подтверждения менеджером. Поставки без даты исключены по умолчанию; их включение — явное допущение. Даты в коротком заголовке «в пути 24.09» получают год даты среза; переход года нужно проверить вручную.

Риск рассчитывается по дневной симуляции остатка и датированных поступлений до срока новой поставки. Сценарная замена количества «в пути» меняет размер заказа, но не создаёт вымышленного графика поступления.

### 6. Объяснимость и экспорт

В карточке показаны исходные компоненты, доокруглённая потребность, минимальная партия, кратность и рекомендованный результат. Исторически исключённый объём и восстановленный stockout выводятся отдельно. Коррекция менеджера не скрывает исходную рекомендацию и отмечается в экспортируемом объяснении.

Сумма закупки — оценка только по товарам с положительной себестоимостью. «СС реал» трактуется как прокси себестоимости; валюта задаётся вручную. Это не утверждённая закупочная цена и не гарантия бюджета. При пересчёте сбрасываются ручные правки и подтверждения, чтобы не сохранить устаревшее решение.

## Универсальный шаблон

Кнопка **Скачать шаблон** формирует книгу с вымышленными примерами. Перед работой замените строки своими данными и проверьте дату среза.

- `Catalog`: `sku`, `code`, `name`, `supplier`, `category`, `cost`, `stock`, `multiple`, `moq`, `lead_days`, `growth_pct`.
- `Sales`: `date`, `sku`, `qty`, `client_id` (только обезличенный!), `order_id`.
- `Stockouts`: `sku`, `start_date`, `end_date` (включительно).
- `Transit`: `sku`, `quantity`, `eta`.
- `Seasonality`: `month` (1–12), `factor`.

Отсутствие поставщика, сроков или закупочной цены не маскируется под фактические данные. При отсутствии справочника поставщик и срок задаются менеджером. Рекомендуется использовать `YYYY-MM-DD` для дат и хранить артикулы/коды как текст.

## Ограничения первой версии

- Нет сервера, учётных записей, общей БД, совместного редактирования и сохранения загруженных данных между перезагрузками.
- Нет автоматической отправки заказов, интеграции с 1С или API поставщиков.
- Используется агрегированный остаток. Отдельное планирование и распределение по складам ещё не реализовано.
- Дату текущего среза и исходные остатки нужно согласовать: изменение даты не восстанавливает историческое состояние склада.
- Нет статистической оценки точности на отложенной выборке, сервисного уровня, финансовой оптимизации или гарантии экономии.
- Нет автоматического распознавания неанонимизированных клиентских сведений: ответственность за анонимизацию входа остаётся у пользователя.
- Ограничение файла — 25 МБ, распакованного XLSX — 120 МБ. Не поддерживаются XLS, XLSB, защищённые паролем книги, ZIP64, макросы и внешние ссылки.
- Неизвестные листы отображаются в журнале и не участвуют в расчёте. XLSX-экспорт не выполняет формулы и записывает числовые результаты как значения.
- Без точных stockout и ID клиента соответствующие требования кейса могут быть продемонстрированы на синтетическом шаблоне, но не подтверждены на исходном наборе партнёра.

## Проверки

Без установки зависимостей, нужен Node.js с поддержкой `structuredClone`:

```bash
node tests/engine.test.cjs
# либо npm test
```

14 проверок: конечные неотрицательные количества; кратность; снижение заказа при росте остатка или товара в пути; влияние срока поставки, сезонности, роста и категории; отдельные MOQ/кратность; нулевая потребность; неизвестный остаток; stockout; поздние поставки; подавление разового месячного пика; распознавание основных отчётов.

При подготовке v0.1 в headless Chromium проверены интерфейс, карточка и симулятор, загрузка шести предоставленных XLSX без ошибок, поиск, изменение настроек, страница поставщика и мобильная ширина 390 px. Из исходных файлов получено 724 объединённых товарных записи, 134 с неизвестным текущим остатком при консервативных настройках. Это результат теста импорта, не экспертно подтверждённое количество активных SKU. Экспорт XLSX повторно открыт и содержит все три листа. Ошибок JavaScript в этом сценарии не зафиксировано. Развёртывание на вашем GitHub выполняется вами по инструкции выше.

## Структура

```text
index.html             Статическая страница и каркас интерфейса
assets/style.css       Дизайн и адаптивная вёрстка
assets/app.js          Экраны, загрузка, сценарии, экспорт, подтверждение
assets/engine.js       Нормализация источников и алгоритм закупки
assets/xlsx.js         Локальный XLSX/CSV reader и XLSX writer без зависимостей
assets/favicon.svg    Значок приложения
tests/engine.test.cjs  Проверки математического ядра
package.json          Необязательные команды тестирования/локального запуска
.nojekyll             Публикация как обычного статического сайта
START_HERE.txt         Короткая инструкция для первого запуска
```

Для дальнейших итераций алгоритм меняется в `assets/engine.js`, интерфейс — в `assets/app.js` и `assets/style.css`. Сборка не нужна.
